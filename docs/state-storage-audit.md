# Durable app-state inventory

This inventory covers `hubitat-mcp-server.groovy` and all 19 libraries it includes. It records the retained `state` and `atomicState` surface, including the two keys reached through the dynamic write-state helpers. Count limits and enforcement caveats come from source; no byte sizes below are live-hub measurements or synthetic estimates.

| Key | Purpose and owner | Count / byte growth | Mutation frequency | Why durable |
| --- | --- | --- | --- | --- |
| `state.accessToken` | Platform-created OAuth token; parent | One platform-sized string | Install and explicit UI rotation | MCP endpoint authentication must survive executions and reloads. |
| `state.ruleToDelete` | Pending custom-rule delete selected in the UI; parent | One rule ID | UI delete flow; removed after confirmation | Confirmation spans separate UI requests. |
| `state.customEngineMigrated` | One-time legacy setting migration marker; parent | One boolean | Assigned idempotently by each `updated()` call | Prevents a later settings save from repeating the compatibility migration. |
| `state.ruleVariables` | Custom-engine fallback variables; parent and variables library | One entry per user-created fallback variable; names and values have no byte cap | Variable set/delete | Values are authoritative user data across executions. |
| `state.headersReadable` | Last observed request-header readability; parent | One boolean | On a detected transition | Suppresses repeated diagnostics and exposes the last observation in `hub_get_info`; protocol handling still reads each request live. |
| `state.originLocalIpReadable` | Last observed local-IP readability; parent | One boolean | On a detected transition | Suppresses repeated diagnostics and exposes the last observation; the Origin allowlist still reads the hub IP live. |
| `state.updateCheck` | Latest release-check result, timestamp, and error; system library | One small record; error/version strings are externally sized | Daily check and first initialization | Drives the update banner and 24-hour check throttle. |
| `state.lastBackupTimestamp` | Latest whole-hub backup time; parent and item-backups library | One timestamp | Backup discovery or creation | Destructive-write authorization spans requests. |
| `state.debugLogs` | Log-level configuration only; parent | Fixed map of `logLevel` and `maxEntries`; history is excluded | Initialization and log-level changes | MCP-set configuration must survive reloads. History lives in native Past Logs and a bounded class buffer. |
| `atomicState.mrtrRequests` | Request-state continuation records; parent via write-state helpers | Separate caps of 16 writes and 8 reads; checkpoint/terminal bytes depend on tool output | Reservation, claim/checkpoint/terminal transitions, and expiry cleanup | Continuation, replay, ownership, and duplicate suppression must survive separate requests. |
| `atomicState.packageDeployInFlight` | Current asynchronous package-deploy lease; self-admin library via `_writeState*` helpers | Zero or one marker; package ref/base URL strings are not byte-capped | Deploy acceptance, phase change, and terminal cleanup | Prevents duplicate deploys across scheduled executions and recompiles. |
| `atomicState.lastSelfDeploy` | Last self-update, restore, or package outcome; code-management, item-backups, and self-admin libraries | One record; error and nested package result have no explicit byte cap | Self-deploy terminal paths | The initiating response can be lost when new code recompiles the app. |
| `atomicState.hubSecurityCookie`, `atomicState.hubSecurityCookieExpiry` | Hub-login session and its expiry; parent | One cookie string and timestamp | Login, 30-minute refresh, authentication failure | Reuse avoids a login round trip on each internal hub request. |
| `atomicState.itemBackupManifest` | Metadata for File Manager source/rule backups; parent, code-management, item-backups, and native-rules libraries | Backup publication/reuse enforces 20 entries, including oversize repair; labels/metadata remain variable-sized | Backup, restore, eviction, and file unlink | Locates exact rollback files without storing source bodies in app state. |
| `atomicState.debugLogGeneration` | Generation fence for native-log recovery; parent | One UUID | First use and explicit log clear | Excludes pre-clear native Past Logs after reload. |
| `atomicState.parentAppIds` | Built-in parent app IDs by native-app type; parent | At most the finite `_appTypeRegistry()` key set | Discovery, invalidation, and legacy-key migration | Parent IDs are hub-specific and expensive to rediscover. |
| `atomicState.inUseHubVars` | Variable names registered as used by custom rules; variables library | At most the current hub-variable names referenced by child rules; name bytes are platform/user-sized | Lifecycle refresh; currently rewritten even when unchanged | Enables Hubitat's warning before a referenced variable is renamed/deleted and supports scoped teardown. |
| `atomicState.variableHistory` | Recent hub-variable change records; variables library | Latest 200 records; values/descriptions remain complete without a byte cap | Every subscribed variable event and matching rename | Preserves subscribed arrival timestamps, rename history and full values across restarts; retained after the compatibility assessment below. |
| `atomicState.hubVarsAppId` | Discovered Hub Variables connector app ID; variables library | One numeric ID | Discovery and invalid-cache removal | Avoids repeated hub-wide connector discovery. |
| `atomicState.predClearPending` | Native Rule Machine app IDs needing predicate cleanup; native-rules library | One generation token per affected rule; removed after cleanup or confirmed deletion | Affected rule-edit and cleanup paths | Carries recovery intent across multi-request edits. The other included libraries (`mcp-app-cloner`, `mcp-bundles`, `mcp-custom-rules`, `mcp-dashboards`, `mcp-debug-logging`, `mcp-devices`, `mcp-discovery`, `mcp-files`, `mcp-hpm`, `mcp-rooms`, `mcp-virtual-devices`, and `mcp-visual-rules`) add no retained local app-state structures. Native-rules references such as `state.allLocalVars` and `atomicState.predCapabs` describe a target Rule Machine app snapshot, not this app's state.

Retired caches `toolSearchCorpus`, `toolSearchTokens`, `toolSearchCorpusVersion`, `toolSearchCorpusFingerprint`, `requiredParamsByTool`, and `requiredParamsByToolFingerprint` may be read or removed for migration, but must not be written to either store. These are the six code-derived keys enforced by the lint guard. `atomicState.publishOutputSchemasForcedOff` is a retired migration marker removed on settings save, outside that derived-cache guard.

Legacy captures now live only in per-app class memory. The first capture-store access imports any old `state.capturedDeviceStates` and `atomicState.capturedDeviceStates` payloads and removes both keys; initialization also invokes this cleanup when either key exists, including empty/null markers. These former user-data keys are outside the derived-cache guard, and neither is an ongoing durable store. Captures are lost on hub restart or app code reload; see [capture-storage.md](capture-storage.md).

Retired metadata cleanup shares one implementation across ordinary requests, settings updates and direct search. It checks key presence (including null markers), removes only existing keys and remembers completion per app in class memory. Failures retry on the next request after a 60-second backoff and log at error level through MCP-accessible diagnostics, including at the default threshold. Native error logging is the fallback if MCP logging fails. Warm completed requests do not access either state store for this migration.

MRTR records arm a single overwriteable expiry job. The callback removes expired records and schedules the next expiry while records remain; an empty store stops scheduling. Live worker ownership protects active records even beyond their timestamp, and expired live owners stop the cleanup timer when there is nothing else eligible to expire. Owner release rearms cleanup; a platform kill that skips release leaves the record protected until class reload, without a repeating idle wake-up. A copy-on-write deadline hint lets warm ordinary requests bypass the write mutex. Cold requests bootstrap scheduling after a class reload and recover a missed callback after a 60-second grace period; initialization rearms after unscheduling. Accepted jobs provide idle cleanup. If scheduling fails and no previously accepted callback remains, retries require another request or lifecycle execution after backoff; platform delays are not a strict deletion deadline.

The ten-minute completed-write replay window, short successful-read markers and full write outcomes are unchanged. Expiry/retention eviction must persist before cache publication or helper cleanup. Optional removal of redundant aggregates from older terminal records builds a copy only when a candidate exists and follows successful eviction separately; its failure preserves replay and retries after 60 seconds. A mixed eviction/compaction migration can still require two writes to preserve that failure isolation; normal terminal records need no compaction write. No additional payload files or per-request full-store scans are introduced. Uninstall removes this app's cleanup and migration hints.

The lint guard detects literal dot/bracket assignments to the six retired derived keys. It does not prove byte bounds, indirect dynamic writes or runtime retention. Focused behavioral tests cover cleanup and recovery; comparable full E2E runtime is the practical performance check. Optional App Stats comparisons can distinguish execution-time changes from deployment/relay time without requiring byte-by-byte profiling.

## Final issue-402 disposition

Backup bodies remain in File Manager; only the shared 20-entry index is durable app state. All source/library/native-rule/pre-restore writers serialize file creation and publication against a per-app committed view. Replacements use a distinct file while the old entry remains published, enforce retention, commit the index, then remove unreferenced files. Optional cleanup failures report an error and leave files available; required backup/publication failures stop the edit or restore. Explicit deletion marks entries pending before removing the file, then unlinks them. Failed deletion restores the entry when possible; even if that reset fails, pending metadata survives and cannot authorize baseline reuse. The shared view replaces the unbounded per-rule baseline mirror, while preserving one-hour reuse and mandatory fresh snapshots. Recompilation rebuilds the view from durable state, failed writes preserve the last committed view, and uninstall drops the app's cache.

Variable history retains its existing durable latest-200 map format, full values, inclusive `sinceMs`, and rename behavior. The native `/logs/eventsJson` reader is not an equivalent replacement: it exposes original event names and event timestamps, whereas this history records subscription arrival time and rewrites prior names on rename. Delegating to the location-event tool would also change the inclusive boundary to strictly-after.

A compact-row candidate was implemented and passed the history regression on GitHub, removing 45 repeated field-name characters per record (9,000 at 200). It was then rejected for a concrete code-rollback incompatibility: the previous reader accesses `entry.name`/`entry.timestamp`, which cannot read positional lists. Restoring the prior app after PR testing would leave its history reader broken. No speedup is claimed or rejected from that experiment; the reason for dropping it is compatibility, not a missing advance benchmark. File-backed history would likewise leave the old app unable to recover the migrated history and would add file publication/recovery plus per-event I/O. That is not adopted as a substitute for the existing compatible history contract. Large full values therefore remain durable state; the original 82,601/937,801-byte examples are synthetic 200-event fixtures, not measured hub sizes. Documentation now correctly states that history survives restart instead of claiming an initialization clear that does not exist.

Predicate recovery generations are compared against the snapshot taken before an already-required `/hub2/appsList` request. Only a structurally complete tree can establish absence, including hidden descendants before output filtering/pagination. New generations created during the fetch, unsuccessful inventories and publication failures retain recovery intent. No TTL or additional inventory request is introduced.

Logging (#406), code-derived metadata and redundant MRTR aggregates (#412), temporary capture payloads (#414), and dependable MRTR expiry/review repairs (#417) are already implemented. BPS/checker/reactive hints have no analogous persisted bulk database; their protections remain. Removed output-schema advertising needs no optimization. Legacy-only `ruleVariables` persistence and `inUseHubVars` rewrites are excluded by the maintainer's scope; existing legacy E2E/BAT stays frozen. Credentials, discovery IDs, deployment receipts, user values, rollback indexes and active/replay recovery data remain durable for their existing contracts. E2E round-trip batching and fixture reuse remain a separate topic. No remaining server-state candidate is silently deferred to another PR.
