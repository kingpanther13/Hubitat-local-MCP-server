# Durable app-state inventory

This inventory covers `hubitat-mcp-server.groovy` and all 19 libraries it includes. It records the retained `state` and `atomicState` surface, including the two keys reached through the dynamic write-state helpers. Count limits and enforcement caveats come from source; no byte sizes below are live-hub measurements or synthetic estimates.

| Key | Purpose and owner | Count / byte growth | Mutation frequency | Why durable |
| --- | --- | --- | --- | --- |
| `state.accessToken` | Platform-created OAuth token; parent | One platform-sized string | Install and explicit UI rotation | MCP endpoint authentication must survive executions and reloads. |
| `state.ruleToDelete` | Pending custom-rule delete selected in the UI; parent | One rule ID | UI delete flow; removed after confirmation | Confirmation spans separate UI requests. |
| `state.customEngineMigrated` | One-time legacy setting migration marker; parent | One boolean | Assigned idempotently by each `updated()` call | Prevents a later settings save from repeating the compatibility migration. |
| `state.ruleVariables` | Custom-engine fallback variables; parent and variables library | One entry per user-created fallback variable; names and values have no byte cap | Variable set/delete | Values are authoritative user data across executions. |
| `state.headersReadable` | Last observed request-header readability; parent | One boolean | On a detected transition | Suppresses repeated diagnostics and exposes the last observation in `hub_get_info`; protocol handling still reads each request live. |
| `state.originLocalIpReadable` | Last observed local-IP readability; parent | One boolean | On a detected transition | Suppresses repeated diagnostics and exposes the last observation; the Origin allowlist still reads the hub IP live. |
| `state.updateCheck` | Latest release-check result, timestamp, and error; system library | One small record; error/version strings are externally sized | Daily check and first initialization | Drives the update banner and 24-hour check throttle. |
| `state.lastBackupTimestamp` | Latest whole-hub backup time; parent and item-backups library | One timestamp | Backup discovery or creation | Destructive-write authorization spans requests. |
| `state.debugLogs` | Log-level configuration only; parent | Fixed map of `logLevel` and `maxEntries`; history is excluded | Initialization and log-level changes | MCP-set configuration must survive reloads. History lives in native Past Logs and a bounded class buffer. |
| `atomicState.mrtrRequests` | Request-state continuation records; parent via write-state helpers | Separate caps of 16 writes and 8 reads; checkpoint/terminal bytes depend on tool output | Reservation, claim/checkpoint/terminal transitions, and expiry cleanup | Continuation, replay, ownership, and duplicate suppression must survive separate requests. |
| `atomicState.packageDeployInFlight` | Current asynchronous package-deploy lease; self-admin library via `_writeState*` helpers | Zero or one marker; package ref/base URL strings are not byte-capped | Deploy acceptance, phase change, and terminal cleanup | Prevents duplicate deploys across scheduled executions and recompiles. |
| `atomicState.lastSelfDeploy` | Last self-update, restore, or package outcome; code-management, item-backups, and self-admin libraries | One record; error and nested package result have no explicit byte cap | Self-deploy terminal paths | The initiating response can be lost when new code recompiles the app. |
| `atomicState.hubSecurityCookie`, `atomicState.hubSecurityCookieExpiry` | Hub-login session and its expiry; parent | One cookie string and timestamp | Login, 30-minute refresh, authentication failure | Reuse avoids a login round trip on each internal hub request. |
| `atomicState.itemBackupManifest` | Metadata for File Manager source/rule backups; parent, code-management, item-backups, and native-rules libraries | Intended shared retention is 20 entries; labels/metadata are variable-sized and legacy oversize handling remains issue 402 follow-up work | Backup, restore, eviction, and file unlink | Locates exact rollback files without storing source bodies in app state. |
| `atomicState.debugLogGeneration` | Generation fence for native-log recovery; parent | One UUID | First use and explicit log clear | Excludes pre-clear native Past Logs after reload. |
| `atomicState.parentAppIds` | Built-in parent app IDs by native-app type; parent | At most the finite `_appTypeRegistry()` key set | Discovery, invalidation, and legacy-key migration | Parent IDs are hub-specific and expensive to rediscover. |
| `atomicState.inUseHubVars` | Variable names registered as used by custom rules; variables library | At most the current hub-variable names referenced by child rules; name bytes are platform/user-sized | Lifecycle refresh; currently rewritten even when unchanged | Enables Hubitat's warning before a referenced variable is renamed/deleted and supports scoped teardown. |
| `atomicState.variableHistory` | Recent hub-variable change records; variables library | Latest 200 records; values/descriptions have no byte cap | Every subscribed variable event and matching rename | Supplies cross-request change history; reducing its state cost remains issue 402 follow-up work. |
| `atomicState.hubVarsAppId` | Discovered Hub Variables connector app ID; variables library | One numeric ID | Discovery and invalid-cache removal | Avoids repeated hub-wide connector discovery. |
| `atomicState.predClearPending` | Native Rule Machine app IDs needing predicate cleanup; native-rules library | One entry per affected rule; no present global cap, removed after cleanup/deletion | Affected rule-edit and cleanup paths | Carries recovery intent across multi-request Rule Machine edits; external-deletion reconciliation remains issue 402 follow-up work. |

The other included libraries (`mcp-app-cloner`, `mcp-bundles`, `mcp-custom-rules`, `mcp-dashboards`, `mcp-debug-logging`, `mcp-devices`, `mcp-discovery`, `mcp-files`, `mcp-hpm`, `mcp-rooms`, `mcp-virtual-devices`, and `mcp-visual-rules`) add no retained local app-state structures. Native-rules references such as `state.allLocalVars` and `atomicState.predCapabs` describe a target Rule Machine app snapshot, not this app's state.

Retired caches `toolSearchCorpus`, `toolSearchTokens`, `toolSearchCorpusVersion`, `toolSearchCorpusFingerprint`, `requiredParamsByTool`, and `requiredParamsByToolFingerprint` may be read or removed for migration, but must not be written to either store. These are the six code-derived keys enforced by the lint guard. `atomicState.publishOutputSchemasForcedOff` is a retired migration marker removed on settings save, outside that derived-cache guard.

Legacy captures now live only in per-app class memory. The first capture-store access imports any old `state.capturedDeviceStates` and `atomicState.capturedDeviceStates` payloads and removes both keys; initialization also invokes this cleanup when either key exists, including empty/null markers. These former user-data keys are outside the derived-cache guard, and neither is an ongoing durable store. Captures are lost on hub restart or app code reload; see [capture-storage.md](capture-storage.md).

Retired metadata cleanup shares one implementation across ordinary requests, settings updates and direct search. It checks key presence (including null markers), removes only existing keys and remembers completion per app in class memory. Failures retry on the next request after a 60-second backoff and log through MCP-accessible diagnostics. Warm completed requests do not access either state store for this migration.

MRTR records arm a single overwriteable expiry job. The callback removes expired records and schedules the next expiry while records remain; an empty store stops scheduling. Live worker ownership protects active records even beyond their timestamp, and expired live owners are revisited after 60 seconds. Ordinary requests bootstrap scheduling after a class reload and recover a missed callback after a 60-second grace period; initialization rearms after unscheduling. Accepted jobs provide idle cleanup. If scheduling fails and no previously accepted callback remains, retries require another request or lifecycle execution after backoff; platform delays are not a strict deletion deadline.

The ten-minute completed-write replay window, short successful-read markers and full write outcomes are unchanged. Expiry/retention eviction must persist before cache publication or helper cleanup. Optional removal of redundant aggregates from older terminal records follows successful eviction separately; its failure preserves replay and retries after 60 seconds. No additional payload files or per-request full-store scans are introduced.

The lint guard detects literal dot/bracket assignments to the six retired derived keys. It does not prove byte bounds, indirect dynamic writes or runtime retention. Focused behavioral tests cover cleanup and recovery; comparable full E2E runtime is the practical performance check. Optional App Stats comparisons can distinguish execution-time changes from deployment/relay time without requiring byte-by-byte profiling.
